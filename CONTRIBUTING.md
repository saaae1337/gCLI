# Как работать над gcli

Правила короткие и конкретные: они экономят время тому, кто пишет код, и
тому, кто читает изменения.

## Требования

Go 1.21 или новее. Больше ничего: у модуля нет внешних зависимостей, все
команды — стандартные.

## Структура

| Путь | Что внутри |
|---|---|
| `src/` | модуль Go (это корень модуля, а не корень репозитория) |
| `builds/` | собранные бинарники, в git не попадают |
| `examples/` | примеры навыков, расширений и команд |
| `build.sh`, `build.cmd` | кросс-сборка всех платформ |

Пакеты внутри `src/`: `core` (типы и хранилище), `providers` (протоколы
провайдеров), `agent` (агентный цикл), `tools` (инструменты), `ui`
(отрисовка), `subagents` (пул субагентов), корневой `main` (REPL и
команды).

## Сборка и проверка

Команды выполняются из `src/`:

```bash
cd src
gofmt -l .                      # неотформатированные файлы: список = проблема
go vet ./...                    # подозрительные места
go build ./...                  # сборка всех пакетов
go test -count=1 ./...          # тесты
go test -race -count=1 ./...    # с детектором гонок — перед коммитом
```

Из корня репозитория — `./build.sh test`, `./build.sh vet`, `./build.sh fmt`,
либо кросс-сборка `./build.sh`. Windows: `build.cmd`.

## Стиль

- Комментарии на русском, объясняют **почему**, а не пересказывают код.
  Формат: `// Имя — что делает.` Затем абзац с причиной решения.
- Пользовательские сообщения — по-русски, без канцелярита.
- Имена тестов описывают свойство и, где возможно, дефект:
  `TestParallelKeepsImages` лучше, чем `TestParallel2`.
- Тест обязан падать на старой версии кода. Зелёный всегда — не проверка.
- Никаких зависимостей без обсуждения: проект сознательно без них.

## Порядок работы

1. Опишите проблему. Дефект часто лежит не там, где виден симптом.
2. Ветка от `master`, имя коммита — Conventional Commits:
   `fix`, `feat`, `refactor`, `test`, `docs`, `build`, `chore`.
3. Напишите тест на дефект **до** исправления и убедитесь, что он падает.
4. Исправление минимальное: меняет поведение, а не переписывает пакет.
5. Прогоните полный набор команд выше.
6. Один коммит — одна мысль. Рефакторинг и правку дефекта не смешивайте.

Формат сообщения коммита: строка до 72 символов, тип в скобках, тело —
отдельным абзацем с объяснением, почему так.

## Границы пакетов

`core` не должен расти без нужды: всё, что можно сделать в `tools`,
живёт в `tools`. Иначе пакет превращается в свалку. `ui` ничего не знает
о провайдерах и не ходит в сеть; `providers` не знает о файлах проекта.

## Безопасность

Любая правка, расширяющая права кода из репозитория, требует теста на
обход. Это касается:

- песочницы файлов (`-sandbox`, `GCLI_SANDBOX`);
- сетевых запросов (SSRF, `GCLI_ALLOW_LOCAL_NET`);
- вывода инструментов (маскирование секретов);
- доверия к навыкам, расширениям и MCP-серверам
  (`/permissions`, `/ext trust`, `/mcp trust`).

Проверяйте обход по границам, а не по «счастливому» случаю: другой
рабочий каталог, симлинк, `..` в пути, IPv4-mapped IPv6 (`::ffff:127.0.0.1`).

## Конкурентность

Ходы идут в горутинах: стриминг размышлений, фоновая печать, пул
субагентов, UI-перерисовка. Общее состояние — под мьютексом, и порядок
блокировок зафиксирован в комментарии (см. `reasonPrint → reasonMu → UI`).
Любая новая горутина, пишущая в состояние приложения, обязана быть под
`-race` в тестах, иначе гонка всплывёт у пользователя.

## Проверка глазами

Изменения интерфейса — цвета, рамки, таблицы, переносы строк, маскот —
нужно посмотреть в настоящем терминале. Тест проверяет ширину в колонках,
а не то, что таблица не разъехалась на узком окне. Снимок экрана снимает
инструмент `screenshot`, но UI-агент доступен только в самом gcli.

## CI и релизы

`.github/workflows/ci.yml` на каждый пуш и pull request:

- **lint** (Linux) — `gofmt -l .` и `go vet ./...`;
- **test** (Linux, Windows, macOS) — `go test ./...`, а на Linux и Windows ещё
  `go test -race`. macOS из гонок исключена сознательно: там она медленнее
  всех, а гонки проекта воспроизводятся на двух других платформах;
- **coverage** (Linux) — `go test -covermode=atomic -coverpkg=./... ./...`:
  один прогон по всем пакетам, иначе профили нельзя сложить в один отчёт.
  `-covermode=atomic` обязателен: иначе счётчики из горутин обновляются без
  синхронизации и профиль считает не то. Результат — в сводку запуска и
  артефактом.

`.github/dependabot.yml` следит только за экшенами: модулей Go нет, так что
проверять нечего, а вот `actions/checkout@v5` вместо v4 появиться может.

`go.mod` должен остаться пустым: внешняя зависимость ломает главное свойство
проекта — собираемость без сети.

`.github/workflows/release.yml` срабатывает на тег `v*` и вручную (кнопка
Run workflow с указанием тега). Он сверяет тег с `var Version` в
`src/core/core.go`, прогоняет тесты, собирает пять платформ, берёт раздел
этой версии из `CHANGELOG.md` и создаёт **черновик** релиза с вложениями
`gcli-*` и `SHA256SUMS.txt`. Черновик публикуется вручную: это последняя
проверка человеком того, что в заметках написано именно то, что вошло в релиз.

Порядок релиза: бамп версии в `src/core/core.go` → раздел в `CHANGELOG.md`
→ тег `vX.Y.Z` → дождаться зелёного CI → собрать релиз из черновика.

## Покрытие тестами

По всему проекту (все пакеты одним прогоном) — около 71%, отдельно пакет
`main` с REPL и командами — около 62%. Ориентир — не процент, а цена
дефекта: роутер команд, разбор аргументов, миссия и цепочка шагов ломаются
тихо, поэтому проверяется не «функция не упала», а состояние, которое
человек увидит потом (файл на диске, счётчик, сессия).

```bash
cd src
# так же, как в CI: одним прогоном по всем пакетам, профили складываются
go test -covermode=atomic -coverprofile=/tmp/cov.out -coverpkg=./... ./...
go tool cover -func=/tmp/cov.out | tail -1   # итог
go tool cover -func=/tmp/cov.out | awk '$3=="0.0%"'   # что не покрыто
```

## Отчёт об ошибке

Полезно указать: версию (`/status`), провайдера и модель, что ожидалось,
что получилось, вызов инструмента с аргументами. Логи — в
`~/.gcli/gcli.log`.
