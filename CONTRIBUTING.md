# Как работать над gcli

Спасибо, что хотите починить что-нибудь. Ниже — короткие правила, которые
экономят время и нервы и вам, и тем, кто читает изменения.

## Требования

- Go 1.21 или новее.
- Ничего больше: зависимостей нет, модуль собирается стандартной командой.

## Сборка и проверка

Модуль лежит в `src/`, а не в корне репозитория. Команды запускаются оттуда:

```bash
cd src
go build ./...           # сборка всех пакетов
go vet ./...             # подозрительные места
gofmt -l .               # неотформатированные файлы (список = проблема)
go test -count=1 ./...   # тесты
go test -race -count=1 ./...  # тесты с детектором гонок — перед коммитом
```

Корень репозитория — не корень модуля: `go build ./...` из `C:\gcli` не
сработает. Если команда «не находит пакет», проверьте рабочий каталог.

## Стиль

- Комментарии на русском, объясняют **почему**, а не пересказывают код.
  Формат: `// Имя — что делает.` Затем абзац с причиной решения.
- Пользовательские сообщения — по-русски, без канцелярита.
- Имена тестов описывают проверяемое свойство и, если возможно, дефект:
  `TestParallelKeepsImages` лучше, чем `TestParallel2`.
- Тест должен падать на старой версии кода. Тест, который зелёный всегда,
  не проверяет ничего.

## Порядок работы

1. Откройте issue или опишите проблему — иногда дефект лежит не там, где виден.
2. Ветка от `master`: `fix(ui): ширина CJK в таблицах`.
   Формат — Conventional Commits: `fix`, `feat`, `refactor`, `test`, `docs`, `build`, `chore`.
3. Пишите тест на дефект **до** исправления и смотрите, как он падает.
4. Исправление — минимальное, меняющее поведение, а не переписывающее модуль.
5. Прогнать полный набор команд выше.
6. Коммит одним куском: рефакторинг и правка дефекта в одном коммите не
   разделяются.

## Чего не делать

- Не менять поведение без теста. «Стал удобнее» — не аргумент, тест — аргумент.
- Не добавлять зависимости без обсуждения: проект сознательно без них.
- Не расширять `core` без нужды: всё, что можно сделать в `tools`, должно
  жить в `tools`, иначе пакет превращается в свалку.

## Безопасность

Любая правка, которая даёт коду из репозитория больше прав, чем раньше,
требует теста на обход. В проекте это касается:

- песочницы (`-sandbox`, `GCLI_SANDBOX`);
- доверия к расширениям и MCP-серверам (`/ext trust`, `/mcp trust`);
- сетевых запросов (SSRF, `GCLI_ALLOW_LOCAL_NET`);
- вывода инструментов (редактирование секретов).

## Отчёт об ошибке

Хороший отчёт содержит: версию (`/status`), провайдера и модель, что
ожидалось, что получилось, и — если дело в инструменте — его вызов с
аргументами. Логи лежат в `~/.gcli/gcli.log`.

## Проверка глазами

Изменения интерфейса (цвета, рамки, таблицы, переносы строк) нужно
посмотреть в настоящем терминале, а не только прогнать тестами: тест
проверяет ширину в колонках, а не то, что таблица не разъехалась на
узком окне.
